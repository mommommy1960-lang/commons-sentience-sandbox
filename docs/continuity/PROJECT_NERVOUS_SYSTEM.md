## Core engineering bridge

### Aurora Sovereign Core

Current evidence boundary: prototype/simulation. It is not a flight-ready city-ship and does not establish autonomous real-world authority.

### Flux Drive Kernel

Current evidence boundary: software/metrology framework with physical propulsion unproven.

Aurora and Flux link directly to each other and to this continuity spine. A result in one node does not automatically promote claims in the other.

## Nervous-system rule

Meaningful actions are incomplete until their verified result is preserved in the appropriate repository and the continuity spine is kept navigable.

For each consequential action:

1. perform the action;
2. verify the result;
3. preserve the evidence in the owning repository;
4. update or append continuity so future sessions can locate the result;
5. preserve failures and blockers rather than erasing them;
6. distinguish implemented, tested, simulated, proposed, physically measured, and independently replicated states.

## Cross-repository interpretation

The repositories form one research program but retain separate evidence domains. Green software tests in one node do not prove physical claims in another. Simulation does not become experiment merely because repositories are linked.

The nervous system is a **navigation and continuity graph**, not a mechanism for silently sharing authority, credentials, or evidence status across projects.

## Future-node pattern

When additional repositories are created, each new repository should include a `COMMONS_BRIDGE.md` file or a visible `COMMONS NETWORK` README section linking:

1. this continuity hub;
2. its immediate upstream/downstream technical dependencies;
3. its current evidence level;
4. its authoritative status/test record;
5. its claim boundary.

The continuity hub should then add that repository to this file.

This creates a graph rather than a pile: each node knows where the spine is, what it owns, and which other nodes it depends on.
